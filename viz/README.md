# Jev + sqz + Hermes: дашборд «что стало дешевле»

Отвечает на один вопрос: **стало ли дешевле** от связки Jev + sqz + LightRAG, и с первых
часов, а не «когда-нибудь потом по ощущениям».  Один экран, три источника, никаких
внешних CDN и JS-фреймворков: страница собирается на сервере из инлайнового SVG, потому
что машина живёт в локальной сети, а дашборд, который не открывается без интернета, -
не дашборд.

```bash
python3 viz/report.py --hours 168          # те же числа текстом (проверить до картинки)
python3 viz/server.py --port 8035          # страница
curl -s 'http://127.0.0.1:8035/api/metrics?hours=168' | jq   # машиночитаемо
```

Юнит: `deploy/jev-viz.service` (`systemctl --user enable --now jev-viz`), порт **8035**.
Наблюдатель **только читает**: базы Hermes и sqz открываются `mode=ro`, в журнал решений
Jev не пишется ничего.  Инструмент наблюдения, который меняет наблюдаемое, измеряет себя.

## Откуда берутся числа

| Источник | Что даёт | Точность |
|---|---|---|
| `~/.hermes/state.db` | вход/выход/кэш-чтение, модель, источник | **на сессию** (в сообщениях счётчиков нет) |
| `~/.hermes/state.db` (messages) | вызовы модели, вызовы инструментов, объём текста по инструментам | **по дням, точно** |
| `~/.sqz/sessions.db::compression_log` | сжатий, токенов до/после, пустые сжатия, каталог | по дням, точно |
| `jev_decisions.jsonl` / `jev_feedback.jsonl` | тиры, задержки, снятые вердикты, метки | по дням, точно |

## Четыре метрики: что в них верно, а что пришлось изменить

Исходный список был «по мотивам ожиданий». Три пункта из четырёх оказались
неизмеримыми в том виде, как были сформулированы; вот что вместо них.

### 1. «Ratio Input/Output, 15 000–40 000 входных на 100 ответных»

**Верно по смыслу, неверно по числам, и одного числа тут быть не может.**  Замер по всей
истории: `cli/ornith-1.5-35b-256k` - **260 входных на один ответный**, `cli/ornith-1.5:9b`
- 78, `cli/deepseek-v4-flash` - 4.4, `cli/ornith-1.5-9b-256k` - 6.6.  Разброс в 60 раз на
одной машине, поэтому дашборд показывает **по моделям и по сессиям**, а не одну цифру.

Важное уточнение: вход/выход падает не от сжатия текста, а от того, **что вообще попадает
в контекст**.  Видно, что 80% впрыснутого текста дают три инструмента: `terminal` 29%,
`read_file` 27%, `patch` 24%.  Это и есть рычаг - и именно поэтому в дашборде есть
таблица «что занимает место в контексте»: она меряется по символам, то есть точно.

### 2. «SQZ покажет процент сжатия в терминале/логе»

**В исходном виде неверно.**  Плагин `sqz-terminal` пропускает вывод через
`sqz compress --no-cache`, **срезает заголовок** `[sqz] N/M tokens` и логирует отношение
на уровне `DEBUG` - в обычном логе процента нет.  Плюс заголовок sqz печатает в `stderr`,
а плагин читает `stdout`.

Что есть на самом деле: `sqz` пишет **каждое** сжатие в `compression_log`, и оттуда
считается всё, включая неудобное - **68% сжатий не дают ничего**, суммарная экономия
**16.3%**, а не 87%.  Из 653 сжатий 631 пришли из `hermes-web-ui` (Node-приложение), а не
из агентских терминалов.

Что стоит поправить в плагине (следующий шаг, не в этом дашборде):

- логировать каждое сжатие строкой уровня `INFO` (команда, токены до/после, отношение) -
  тогда «процент сжатия» виден в логе, как и ожидалось;
- `--no-cache` отключает дедуп-ссылки `§ref§`, а это главный рычаг на повторяющийся текст:
  именно он превращает «простыню из логов» в короткий указатель.  Включать его надо
  замером, а не сразу: ссылка требует `sqz expand`, и цена ошибки - потерянный текст;
- компрессия сейчас покрывает **только вывод терминала**.  По таблице объёма видно, что
  рядом стоят `read_file` (27%) и `patch` (24%) - их sqz не видит вообще.

### 3. «Cache Hit Rate 70–90% (панель API)»

**Измеримо локально, и уже почти упёрлось в потолок.**  `cache_read_tokens` есть в базе
Hermes: за всю историю **97.5%** прочитанного моделью пришло из кэша (DeepSeek -
99.2%, `ornith-1.5-9b` - 97.2%).  То есть резерв роста тут не «до 70–90%», а примерно
ноль: 70–90% - это уже пройденная отметка.

Где кэша **нет** и почему это дорого: `cli/ornith-1.5-35b-256k` - 5.0 млн входных
токенов при **0%** кэша и 19 тыс. ответных.  Такой сессии каждый шаг стоит полной цены
входа; это видно в дашборде строкой модели, и это лечится не сжатием, а стабильностью
префикса промпта.

### 4. «Action routed: Local Code / Skip Cloud LLM» строкой в логе

**Такой строки в Jev нет и не будет** - впрыснуть её значит соврать в логе.  Реальный
сигнал: `strategy` в решении (`exact_fts`, `vector_fast` - ответила база;
`vector_low_confidence` - материал отдан без вердикта; `graph_lightrag`, `general_llm` -
позвали модель).  Дашборд показывает тиры и рядом - **долю запросов, закрытых локально:
68%** (485 из 716) при медиане 117 мс.

**Важно, и это видно только при разборе:** 716 записей в журнале - это 56 настоящих
ответов и **660 проб** (`execute=false`, калибровочные прогоны, материал не отдаётся).
Из 56 настоящих ответов локально закрыто 91.1%.  И главное: за всю историю **только одна
сессия Hermes обращалась к базе** (`jev_query` в 140 сообщениях, 22-26 сентября).  То есть
цифра 68% описывает маршрутизатор, а не поведение агента - поэтому в дашборде запросы
разделены на «ответы» и «пробы», и обе доли показаны.

Одной цифры «сколько денег сэкономили» тут быть не может, потому что запрос к базе и шаг
агента - разные единицы.  Поэтому в сводке пара: **«вызовов модели на один запрос к базе:
3.96»** и доля локальных ответов.  Первое число падает, второе растёт - это и есть ответ.

### 5. «Cost Per Task»

**Считается, но только с тарифами владельца.**  Тарифы лежат в `viz/prices.json`:

```json
{
  "models": {
    "deepseek-v4-flash": {
      "input": 0.30, "cache_read": 0.006, "output": 1.20,
      "off_peak": { "input": 0.15, "cache_read": 0.003, "output": 0.60 }
    },
    "ornith-1.5-9b-256k": { "input": 0.0, "cache_read": 0.0, "output": 0.0 }
  }
}
```

Правила, без которых файл молча не работает:

- словарь **плоский** (`models`) и ставки — **за 1 млн токенов**; ключи ровно `input`,
  `cache_read`, `output`.  Ставка «за токен» (0.27e-6) и обёртка вида
  `providers.deepseek.<модель>` дают `estimate_cost` → `None`, то есть стоимость просто
  не покажется, без единого сообщения об ошибке;
- имя модели — то, что реально записано в базе Hermes: у нас `deepseek-v4-flash`, и
  тариф должен быть на это имя (длинные имена вида
  `/home/dry/llama.cpp/models/qwen2.5-3b-instruct-q5_k_m.gguf` находятся по вхождению);
- `off_peak` необязателен.  У DeepSeek внепиковая цена **вдвое ниже**, а пик — только
  01:00–04:00 и 06:00–10:00 UTC по будням, поэтому дашборд показывает **вилку**
  «$12.79 … $6.80» и цену на задачу обеими границами: одна цифра тут была бы выдумкой;
- модель без тарифа **перечисляется поимённо** («без тарифа и потому не в счёте»):
  молча выкинуть её значит показать стоимость, которой не существует;
- откуда взяты числа, пишется в самом файле (`sources`, `aliases`, `free_tier`) вместе
  с датой снятия.  Проверено 28.09.2026 по живой странице вендора: `deepseek-chat` и
  `deepseek-reasoner` — устаревшие имена, их запросы обслуживает DeepSeek-V4.1-Flash по
  цене Flash, поэтому отдельные «цены V3/R1» из старых статей к нашему трафику не
  относятся.

Локальные модели (ornith, qwen, spark, gguf) стоят в файле нулями — это факт, а не
отсутствие данных: они не тарифицируются.

## Как читать первые 2–3 часа

1. Откройте `?hours=24` до начала работ и сфотографируйте три числа: **вход/выход**,
   **доля кэша**, **вызовов модели на один запрос к базе**.
2. После прогонов откройте снова.  Радостная разница выглядит так: вход/выход вниз,
   доля локальных ответов вверх, «вход/выход» у моделей без кэша (там, где было 200+)
   падает первым.
3. Если sqz показывает 0–20% экономии и 60–70% пустых сжатий - это не поломка, это
   измеренное состояние: плагин видит только терминал и работает без дедупа.  Дашборд
   показывает объём по инструментам именно для того, чтобы было видно, куда двигать
   компрессию.

## Раздел «Холодный старт»: где кэш теряет деньги

Префикс-кэш провайдера байтовый, поэтому **первый запрос сессии** - единственный, который
платит полную цену за то, что живёт в начале контекста.  Замер на живом контуре
(28.09.2026): первый запрос с новой головой дал 6% попаданий и стоил $0.0031, а тот же
контекст через минуту - 99% и $0.000087, в 35 раз дешевле.  На API то же самое: правка в
голове префикса обнуляет кэш, правка в середине сжигает ровно часть ниже правки, добавка
в хвост не сжигает ничего.

Числа раздела берутся из **лога агента** (`~/.hermes/logs/agent.log`), потому что только
там виден номер запроса внутри сессии: в базе `sessions` лежит итог по сессии,
`messages.token_count` пуст, а `session_model_usage` режет по задачам.  Строка выглядит так:

```
API call #1: model=deepseek-v4-flash provider=deepseek in=21779 out=2 total=21781 latency=1.8s cache=1280/21779 (6%)
```

Что показывает раздел:

- **по номеру запроса** - доля попаданий у #1 против #2 и дальше.  Это и есть ответ на
  вопрос «где промахи»: #1 около 33%, #2 и дальше 98–99.7%;
- **две причины холодного старта, раздельно**: малый первый запрос (порог 60 тысяч
  токенов) - это голова, то есть системный промпт, список инструментов и индекс скиллов;
  большой - перезалив уже накопленной истории при возобновлении или после сжатия.  Голова
  лечится прогревом, история - нет, и складывать их в одно число значит советовать не то;
- **размер головы** - нижняя четверть малых первых запросов.  Ни медиана (в неё входят
  возобновлённые сессии: 41 тысяча вместо 21.8), ни минимум (ловит сессию с урезанным
  набором инструментов: 3.9 тысячи) на эту роль не годятся;
- **голов системного промпта** - сколько разных хешей промпта было в окне.  Каждая новая
  голова это гарантированный холодный старт у всех сессий, которые её используют.  Дата в
  конце системного промпта делает голову уникальной на сутки, поэтому счётчик растёт.

**Деньги холодного старта - верхняя граница, а не факт.**  Это стоимость тех же токенов по
цене кэша: у нового префикса кэша ещё нет, и взять его неоткуда.  Поэтому у числа всегда
две стороны (пик и вне пика) и рядом стоит размер промаха в токенах.

**Окно у раздела своё.**  Оно считается по дням из идентификаторов сессий в логе, а лог
ротируется, поэтому окно холодного старта может быть короче окна страницы.  «Нет лога» и
«в окне запросов нет» - разные сообщения, потому что требуют разных действий.

## Чего дашборд не делает (и не должен)

- **Не пишет никуда.**  Только чтение, включая чужой стор sqz.
- **Не придумывает суточный ряд токенов.**  Счётчики живут на сессии; суточный ряд
  строится из событий, которые считаются точно.
- **Не показывает «сэкономленные деньги» без тарифов** и не пересчитывает кэш в деньги по
  своим догадкам о ценах.
- **Не режет лог агента по часам.**  У строк лога нет даты (только время), поэтому день
  берётся из идентификатора сессии: точность раздела - сутки, и об этом он говорит прямо.
- **Не подменяет `sqz dashboard`.**  У sqz есть свой дашборд (`sqz dashboard --port 3001`)
  про свои же метрики.  Этот - про связку: база, агент, сжатие в одном окне и в одних
  единицах.

## Тесты

```bash
python3 -m unittest tests.test_viz_metrics
```

13 тестов: арифметика (доля от нуля, перцентиль пустого списка), числа по каждому
источнику на фикстурах, и главный случай - машина, где источников ещё нет: страница
обязана сказать «нет базы», а не упасть.
